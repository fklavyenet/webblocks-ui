JavaScript

Nutze das JavaScript des Pakets für Interaktion. Nutze CSS für Layout und passive Darstellung. Diese Grenze ist wichtig.

Richtige Aufteilung der Zuständigkeiten Layout wird über Layout- und Pattern-Klassen von CSS bestimmt. Overlays, Tooltips, Tabs, Drawers, Theme-Controls, Passwort-Sichtbarkeit, Command Palette und Dismiss-Abläufe werden über ausgelieferte Hooks und öffentliche APIs von JavaScript bestimmt.

Konventionen für Verhalten

Kleine Module

Das Bundle bleibt lesbar, weil Verhalten in benannte Module aufgeteilt ist statt in eine große anonyme Runtime.

Benannte APIs auf window

WBTheme, WBModal, WBGallery, WBDrawer, WBToast und verwandte Module bleiben aus der Konsole heraus einsehbar.

Daten-Hooks im Markup

Die meisten Interaktionen starten über data-wb-*-Attribute, damit das HTML weiterhin verrät, was sich öffnen, schließen oder ändern kann.

Trigger-Modell

<button data-wb-toggle="modal" data-wb-target="#confirm-dialog">
  Löschen
</button>

<button class="wb-gallery-trigger"
        data-wb-gallery-target="#media-viewer"
        data-wb-gallery-full="/images/demo-full.jpg">
  Galerie-Element öffnen
</button>

<button data-wb-cookie-consent-open data-wb-target="#siteCookiePreferences">
  Cookie-Einstellungen
</button>

<button data-wb-mode-set="dark">Dunkel</button>
<button data-wb-dismiss="modal">Schließen</button>

Das meiste Verhalten beginnt mit einem kleinen Attribut-Vertrag. Nutze data-wb-toggle="modal" für direkte Modal-Trigger, lass data-wb-gallery-target Inline-Galerie-Elemente zu einem gemeinsamen, inhaltszentrierten Modal-Viewer aufwerten, und verwende die Cookie-Consent-Hooks, wenn ein Projekt einen wiederverwendbaren Einwilligungs- und Wiederöffnungs-Flow braucht.

Theme und Dropdown

wb-overlay-root ist gemeinsame Top-Layer-Infrastruktur. Verankerte Overlays rendern dort im JS-Modus, um Abschneiden zu vermeiden, Gallery-Viewer laufen über die gemeinsame wb-modal-Basis, und Toast-Container können dort liegen, ohne in den normalen Layoutfluss einzutreten.

Aufbau der API

WBTheme.setMode('dark')
WBTheme.setAccent('forest')
WBTheme.setRadius('soft')
WBTheme.setDensity('compact')
WBModal.open(document.getElementById('my-modal'))
WBGallery.open(document.querySelector('.wb-gallery-trigger'))
WBDrawer.open(document.getElementById('my-drawer'))
WBPasswordToggle.toggle(document.querySelector('[data-wb-password-toggle]'))
WBToast.show('Gespeichert', { type: 'success' })
WBToast.show('Entwurf gespeichert', { type: 'info', duration: 7000 })
WBToast.show('Zustellung fehlgeschlagen', { type: 'danger', duration: 0 })
WBCookieConsent.open()
WBCookieConsent.clear()

Nutze die öffentliche API, wenn du wirklich imperative Kontrolle brauchst. Existiert bereits ein deklarativer data-wb-*-Trigger, gib zuerst diesem Markup-Weg den Vorzug.

Toast-Feedback WBToast ist für kurzlebiges, nicht blockierendes Erfolgs- und Info-Feedback gedacht. Success- und Info-Toasts verschwinden standardmäßig von selbst; Warn- und Fehler-Toasts bleiben bestehen, sofern kein Timeout ausdrücklich gesetzt wird. Validierungsfehler, vom Nutzer korrigierbare Fehlschläge, dauerhafte Warnungen und blockierende Fehler sollten inline nahe am zugehörigen Formular, an der Card oder am Abschnitt erscheinen - mit kontextbezogenem Feedback wie wb-alert.
